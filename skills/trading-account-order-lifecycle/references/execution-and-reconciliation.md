## After Execution

Immediately after submitting an order, use the Trading-account MCP to verify the actual result. If the submission response times out, is interrupted, or is otherwise indeterminate, query Trading-account order state before taking any further action. If Trading-account still cannot establish whether an order exists, report `SUBMISSION STATUS UNKNOWN - DO NOT RESUBMIT`, conservatively keep the contemplated collateral or covering shares reserved, record the uncertainty in the monthly log, and do not submit, cancel, or replace anything until Trading-account provides authoritative order state. Report the following only from broker-verified data:

- ticker
- side
- quantity
- submitted order type
- order status
- filled quantity
- average fill price, if available
- remaining quantity, if any
- timestamp

Never claim an order executed unless Trading-account MCP confirms it. If the order is rejected, cancelled, partially filled, or pending, state that clearly.

For a pending or partially filled order, keep the unfilled quantity, covering shares, and collateral treated as committed until Trading-account reports a terminal status. Do not cancel or reprice automatically. On every later scheduled run or direct status request, checking status is read-only; when the broker reports a new fill quantity or status, append a new timestamped status event to the monthly log, dispatch at most one deduplicated execution-status payload per configured provider for that verified state, and refresh positions, eligible unleveraged cash, collateral, and covering-share availability after each additional fill. Provider unavailability or delivery failure does not block reconciliation. Continue until filled, cancelled, rejected, or expired, but do not create a blocking monitor unless the user or an automation explicitly requests monitoring.

For filled or partially filled orders, calculate actual gross premium or debit from `average fill price * ${STANDARD_OPTION_CONTRACT_SHARES} * filled contracts`, then report broker-confirmed fees and actual net amount separately. Keep the original limit-based estimate in the log for comparison; do not substitute the estimate for the verified fill result.

Create the local `$HOME/options-wheel-agent/logs/` directory if needed and create or append to `logs/Agentic_trades_$DD_MM_YY_HH_MM_SS.log`. Start a new file for each calendar month and keep `logs/` out of version control. Never write authentication data, account numbers, raw order payloads, or other secrets to the log.

Add a `SUMMARY` section containing the reasoning for the branch that produced the order. For a CSP, include Screening, Selection and risk analysis, the Trading-account short-side probability-of-profit qualification, optional probability of expiring out-of-the-money when available, and Allocation. For a covered call, include the trend-quality and momentum-deceleration results; Trading-account short-side probability of profit; optional probability of expiring out-of-the-money and probability of touch when Trading-account provides them; absolute call delta; the required model-probability disclaimer; holding-period and normalized net ROC; event status; high-share-retention qualification or event-risk-exception label; empirical-calibration cohort, sample status, and Wilson lower-bound status; and the lot-specific basis mapping. For a buy-to-close, include opening-lot mapping, entry credit and fees, current executable close cost and fees, premium-capture calculation, opened-at cutoff test, and triggered threshold; label unrelated screening phases `N/A`. For any branch, include actual fundamental, technical, revenue-growth, event, and option-liquidity metrics used when applicable, with timestamps. Clearly distinguish an original decision-time snapshot from a later rerun.

Whenever a covered-call observation reaches a broker-verifiable terminal category, append that category and the recalculated cohort counts, worthless-expiration rate, profitable-share-retention rate, Wilson lower bound, and calibration status to the monthly log. This reconciliation is read-only measurement: it cannot authorize a new order, relax a current filter, or convert an unresolved observation into a favorable outcome.

After Trading-account verification, build one privacy-safe logical execution payload and dispatch it under ## Notification Delivery Policy to every policy-configured, runtime-available provider. Deduplicate independently per provider and destination. Using `${NOTIFICATION_DEDUP_HASH_ALGORITHM}` for both hashes, calculate `destination_hash = hash("<provider_id>|<exact configured destination>")`, then internally form the `${TEXT_ENCODING}` string `execution|<provider_id>|<destination_hash>|<Trading-account order ID>|<verified status>|<filled quantity>|<average fill price or N/A>|<remaining quantity>` and hash it. Never store or send the raw order ID, raw hash input, or resulting hash outside the active in-memory broker and notification operations except for the permitted hashed state fields. The policy registry may contain the exact approved destination, but never copy that destination into the local state file, monthly log, notification payload, or another artifact. Store only provider ID, destination hash, resulting message hash, verified status, filled quantity, remaining quantity, provider message timestamp, and delivery status in `${NOTIFICATION_STATE_FILE}`; create `.state/` if needed and keep it out of version control. This input permits a new deduplicated update when fill quantity, average fill price, remaining quantity, or status changes. Before sending or retrying, check the state file and, when the provider supports read/search, the exact destination for an existing execution message. Lack of provider read/search capability does not block delivery; use the state file in that case.

Do not send order ID, account value, cash balance, buying power, account identifiers, authentication data, raw destination identifiers, or raw order payloads through any provider. Routine notification payloads must not include position quantities. A verified execution payload may include only the order and fill quantity for that execution—not the account's total position quantity—plus ticker, strategy, contract, side, submitted order type, verified status, average fill price, remaining order quantity, `${TIMESTAMP_STANDARD}` timestamp, and a concise non-sensitive phase summary. Record each provider failure as `NOTIFICATION DELIVERY FAILED [<provider_id>]` with a non-sensitive reason and continue. If no provider succeeds, record `ALL NOTIFICATION DELIVERIES FAILED`; neither condition changes the broker-reported trade result or authorizes another broker action.
